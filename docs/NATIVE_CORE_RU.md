# Отдельный аналитический companion на C++23

Companion строит локальный отчёт по журналу TankSession Analytics: общую сводку и группы техники, суммы, средние, известность данных, долю побед, разброс и перцентили. Это рабочий путь `battles.jsonl → Python 3 → отдельный процесс C++23 → отчёт JSON или текст`.

Он работает вне игрового процесса. DLL в клиент не внедряется, игровой Python 2.7 не запускает subprocess, архив companion не копируется в папку модов. Игровой мод продолжает собирать историю своим прежним механизмом. Проверки companion не заменяют нативную приёмку мода и Gameface.

## Запуск готового архива

Для Windows x64 нужен архив `TankSession_Analytics_<version>_Native_Windows_x64.zip`, для Linux x64 — `TankSession_Analytics_<version>_Native_Linux_x64.zip`. `<version>` берётся из `src/meta.xml` при сборке. Рядом публикуется `.zip.sha256`; внутри находятся `manifest.json` с хешами файлов, готовый C++ executable, Python adapter, необходимые чистые Python-модули, инструкция, лицензия и вымышленные примеры. Компилятор, CMake и GoogleTest конечному пользователю не нужны. Для чтения журнала требуется **Python 3.9+**.

Распакуй весь архив в отдельный каталог. В Windows открой терминал в этой папке:

```bat
native_report.cmd --data sample_data/battles.jsonl --account demo
native_report.cmd --data "D:\Games\Tanks\mods\configs\tanksession_analytics\battles.jsonl" --account ACCOUNT_ID --json --output report.json
```

На Linux:

```sh
./native_report.sh --data sample_data/battles.jsonl --account demo
./native_report.sh --data /path/to/battles.jsonl --account ACCOUNT_ID --output report.txt
```

Если распаковщик потерял Unix-права, выполни `chmod +x native_report.sh bin/tanksession-native`. Windows launcher использует `py -3`, а при отсутствии `py` — команду `python` из `PATH`. C++ executable Windows собирается со статическим MSVC runtime; Linux-артефакт предназначен для среды, совместимой с использованной Linux CI-сборкой. Наличие Linux-бинарника не означает поддержку игрового клиента на Linux.

`ACCOUNT_ID` — один подтверждённый аккаунт, история которого уже есть в журнале. Его значение не попадает в отчёт и не передаётся C++ процессу. Аккаунты `local`, `unknown`, пустой и `0` не выбираются: принадлежность такой истории не установлена. Отчёт показывает количество исключённых записей других аккаунтов, количество этих аккаунтов и число записей без владельца.

По умолчанию выполняется native-расчёт. Если executable отсутствует, вернул ошибку, завис или нарушил протокол, отчёт завершается с ошибкой. Явный `--engine python` включает независимую Python-реализацию для сверки; скрытого переключения нет.

## Фильтры и сохранение

```sh
python tools/native_report.py --data sample_data/battles.jsonl --account demo --vehicle IS-7 --from 2026-11-01 --to 2026-11-30 --json
```

`--vehicle` принимает устойчивый selector или однозначную точную старую подпись. `--from` и `--to` включают указанные **даты получения результата в UTC**. Это не время начала боя. Запись без пригодного timestamp остаётся в отчёте без календарного фильтра; при заданном диапазоне она учитывается среди исключённых фильтром. Часовой пояс компьютера не меняет выборку.

Без `--json` печатается читаемый текст; `--top 20` ограничивает число показанных групп, но не общую сводку. JSON содержит все группы. `--output report.json` или `--output report.txt` сохраняет результат атомарной заменой указанного файла. Путь исходного журнала нельзя использовать как путь отчёта.

Чтение использует существующий `BattleStore`: повреждённые строки диагностируются, append-only ревизии объединяются, дубликаты не становятся новыми боями. Сам журнал, pending, профили и цели не изменяются. Диагностика физического журнала включена в отчёт отдельно от числа выбранных логических боёв.

## Граница ответственности

| Слой | Ответственность |
|---|---|
| `BattleStore` и Python-валидация | Схема записи, допустимые числа, дедупликация, fill-missing ревизии и конфликты |
| `vehicles.resolve_records` | Только выбранный аккаунт, точные подтверждённые aliases, сохранение неоднозначных legacy-групп |
| `tools/native_report.py` | Фильтры UTC, стабильный порядок, dense group IDs, числовой IPC, запуск executable, проверка ответа и подписи |
| `ts_native_core` | Чистые числовые расчёты, без знания аккаунта, арены, подписей и игрового API |
| `tanksession-native` | Ограниченный парсер stdin, вызов ядра и единственный JSON-ответ stdout |

Сначала определяется принадлежность аккаунту, затем строятся aliases. Наблюдение другого аккаунта не может дать идентичность старой строке. В C++ отправляется числовой номер группы, а не ID аккаунта, арены или подпись. Python возвращает selector и последнюю известную подпись в результат. Для неоднозначной старой группы сохраняется `identity_ambiguous: true`: описательная сводка не подтверждает, что это одна машина, и не является заключением о прогрессе.

## Протокол 1

Вход C++ — ASCII с полями через TAB. Это узкий протокол между двумя компонентами проекта, а не альтернативный импорт JSONL.

```text
TSA_NATIVE<TAB>1<TAB>row_count<TAB>group_count<LF>
group_id<TAB>outcome<TAB>damage<TAB>xp<TAB>xp_base<TAB>xp_bonus<TAB>credits_net<LF>
```

Пустое значение записывается как `?`, известный ноль — как `0`. Исходы: `0` неизвестен, `1` победа, `2` поражение, `3` ничья. Group IDs идут от `0` до `group_count - 1`, каждая объявленная группа должна иметь хотя бы одну строку. При пустой выборке оба счётчика равны нулю. Принимаются LF и CRLF, требуется завершающий перевод строки. Лишние строки, столбцы, пробелы внутри чисел, дроби, экспоненты, `NaN`, неканонические числа, обрыв и неизвестная версия отклоняются целиком.

Ограничения: **1 000 000 собственных записей, 4096 групп, 256 байт в строке, абсолютное значение метрики не выше 10¹²**. Отрицательные значения допустимы только для `credits_net`. Сумма по такому диапазону ограничена 10¹⁸ и помещается в signed 64-bit integer. Python явно сообщает о значении вне диапазона companion; оно не превращается в пропуск. Исходный schema-1 журнал допускает более широкий диапазон — ограничение относится к этому отчёту. Для файла журнала установлен предел 512 МиБ, для принимаемого JSON-ответа — 32 МиБ. Последний предел проверяется при разборе ответа, это не системная квота памяти стороннего executable; запускай собранный проектом бинарник.

Выход executable содержит `protocol`, `definitions`, `overall`, `groups`. В каждой группе есть `id` и `statistics`. Wrapper добавляет `engine`, `source`, `selector`, `label`, `identity_ambiguous`. Суммы кодируются точными десятичными **строками**, чтобы JavaScript не округлил большие целые. Нет известных значений — `sum: null`; известный нулевой итог — `sum: "0"`.

| Поле | Определение |
|---|---|
| `battles`, `wins`, `losses`, `draws`, `outcomes_known` | Число записей и известных исходов; неизвестный исход не считается поражением |
| `win_rate` | `100 × wins / outcomes_known`; `null`, если исходы неизвестны |
| `known`, `missing`, `coverage_pct` | Известность каждой метрики; доля от всех выбранных записей группы |
| `sum`, `mean`, `min`, `max` | Только известные значения; пропуски не добавляют нули |
| `sample_variance` | Выборочная дисперсия с делителем `n - 1`; `null` при `n < 2` |
| `stddev` | Квадратный корень выборочной дисперсии |
| `p50`, `p90` | Перцентили R7: линейная интерполяция в позиции `(n - 1) × p` отсортированной выборки |
| `coefficient_of_variation` | `stddev / mean`, только для неотрицательных метрик при `n ≥ 2` и `mean > 0`; для чистого дохода всегда `null` |

Сумма точная, среднее и разброс представлены floating point. Ядро использует Welford с предварительным целочисленным центрированием относительно первого наблюдения: небольшой разброс около большого среднего сохраняется лучше, чем при вычислении `mean(x²) - mean(x)²`. Порядок строк и JSON фиксирован; повторный запуск одного executable с одним входом воспроизводим. Между компиляторами допустима малая floating-point разница, проверяемая tolerance в parity tests. Побитовая идентичность результатов разных платформ не обещается.

CV описывает относительный разброс наблюдений. Это не рейтинг навыка, рекомендация тактики или основание сравнивать смешанные классы и режимы. Перцентили доступны и на малой выборке, но `known` всегда виден; статистическое утверждение о прогрессе из них автоматически не строится.

## Сборка и тесты

Нужны CMake 3.24+, компилятор с C++23 и совместимая standard library со `std::expected`. CMake включает `CXX_STANDARD_REQUIRED` и запрещает compiler extensions. Ядро — static library; executable не имеет сторонних runtime-библиотек проекта. [CMake описывает выбор стандарта и обязательность его поддержки](https://cmake.org/cmake/help/latest/prop_tgt/CXX_STANDARD.html).

Команды этого раздела выполняются в корне клонированного репозитория. Готовый пользовательский ZIP содержит executable и adapter, а не toolchain или весь исходный C++ проект.

```sh
cmake -S native -B native/build -DCMAKE_BUILD_TYPE=Release
cmake --build native/build --config Release --parallel 2
ctest --test-dir native/build -C Release --output-on-failure
```

GoogleTest 1.17.0 закреплён полным commit SHA [`52eb8108c5bdec04579160ae17225d66034bd723`](https://github.com/google/googletest/commit/52eb8108c5bdec04579160ae17225d66034bd723). Он загружается только при конфигурации тестовой developer/CI-сборки через `FetchContent`, не при запуске companion и не при установке модификации. [Официальный CMake quickstart GoogleTest](https://google.github.io/googletest/quickstart-cmake.html) описывает эту интеграцию. Для сборки executable без тестовой зависимости укажи `-DBUILD_TESTING=OFF`; для offline-тестов можно задать `FETCHCONTENT_SOURCE_DIR_GOOGLETEST` с заранее полученным проверенным исходником.

Цели: `ts_native_core`, `tanksession-native`, `ts_native_tests`, `ts_native_benchmark`. Executables всех конфигураций лежат в `native/build/bin/`; на Windows имеют расширение `.exe`.

Linux/macOS shell, parity с реальным executable:

```sh
TANKSESSION_NATIVE_BINARY=native/build/bin/tanksession-native python -m unittest discover -s tests -p 'test_native_report.py' -v
```

PowerShell:

```powershell
$env:TANKSESSION_NATIVE_BINARY = (Resolve-Path native/build/bin/tanksession-native.exe)
python -m unittest discover -s tests -p test_native_report.py -v
```

Проверки сравнивают результат с независимой Python-реализацией на основе `statistics`: рандомизированные пропуски/исходы/группы, отрицательные кредиты, большие близкие числа, пустая и единичная выборки. Отдельные тесты проверяют account isolation, legacy aliases, readonly-ревизии, строгий парсер, обрыв протокола, сохранение нуля, несовместимый ответ executable и отсутствие скрытого fallback. Без явно настроенного `TANKSESSION_NATIVE_BINARY` только executable parity-класс пропускается; это не выдаётся за нативную проверку.

Для GCC/Clang есть AddressSanitizer + UndefinedBehaviorSanitizer:

```sh
cmake -S native -B native/build-asan -DCMAKE_BUILD_TYPE=Debug -DTSA_ENABLE_SANITIZERS=ON
cmake --build native/build-asan --parallel 2
ctest --test-dir native/build-asan --output-on-failure
```

## Измерение производительности

```sh
native/build/bin/ts_native_benchmark 100000
python tools/benchmark_native.py --binary native/build/bin/tanksession-native --sizes 1000 10000 100000 --repeats 3 --json
```

Первый инструмент измеряет только ядро на заранее подготовленных числовых строках. Второй использует синтетический аккаунт, 32 группы и явные пропуски. После прогрева берётся медиана трёх запусков. Native-время включает кодирование input, запуск процесса, парсер, расчёт, разбор/валидацию JSON и возврат подписей. Общая для обоих движков подготовка Python измеряется отдельно; чтение файла и генерация синтетических данных не входят во время движка. Python-reference использует независимую точную реализацию дисперсии; это не существующий dashboard и не замер игрового FPS.

Локальный запуск 27 ноября 2026, Linux x86_64/glibc 2.41, GCC 14.2.0 Release, Python 3.12.14:

| Записи | Общая Python-подготовка | Native с subprocess и протоколом | Python reference |
|---:|---:|---:|---:|
| 1 000 | 0,0208 с | 0,00614 с | 0,00976 с |
| 10 000 | 0,2408 с | 0,02611 с | 0,04840 с |
| 100 000 | 2,3437 с | 0,22293 с | 0,55824 с |

Чистое C++ ядро на 100 000 строках: медиана **0,0416 с**. Главный расход полного пути на этом наборе — Python-валидация и проекция идентичности. Таблица не обещает такой же результат на другом компьютере и не утверждает ускорение всей системы в отношении native/reference. Точное окружение, SHA-256 executable и результаты сохранены в [`native/benchmarks/baseline-linux.json`](../native/benchmarks/baseline-linux.json).

## Упаковка

```sh
python tools/package_native.py --binary native/build/bin/tanksession-native --platform linux-x64
```

Windows CI использует `--binary native/build/bin/tanksession-native.exe --platform windows-x64`. `Windows` и `Linux` принимаются как aliases. Версия берётся из `src/meta.xml`; имя содержит `Native_Windows_x64` или `Native_Linux_x64`. Пакетчик проверяет формат/архитектуру executable и его `--version`, включает фиксированный allowlist, задаёт постоянные ZIP timestamps и permissions, пишет manifest и SHA-256 sidecar. Для одного набора входных байтов и source commit архив воспроизводим. GoogleTest, build cache, private journal, профили и установщик игрового мода в этот архив не входят.

## Как объяснять архитектуру на собеседовании

Начни с задачи: повторяемая сводка большой локальной истории с неполными метриками и устойчивой идентичностью техники. Затем объясни границу доверия: уже существующий Python-код отвечает за данные аккаунта, а C++ получает ограниченную числовую задачу. Это позволяет проверить расчёты независимо и исключает зависимость игрового процесса от новой C++ интеграции.

В коде можно показать `std::span` как невладеющее представление входного batch, `std::expected<Report, Error>` для явного результата/ошибки, RAII-контейнеры без ручного управления памятью и bounded `from_chars`-парсер. Обоснуй выбор числового протокола: свободные строки и JSONL остаются в Python, поэтому C++ не нужен универсальный JSON parser или доступ к приватным идентификаторам. Интерфейс версионируется и покрыт malformed-input тестами.

Для статистики покажи различие нуля и пропуска, denominator доли побед, выборочную дисперсию, причины центрирования и точные суммы строками. Для инженерного качества — pinned test dependency, CTest, ASan/UBSan, parity с независимым reference, проверку извлечённого готового архива и benchmark, отдельно раскрывающий стоимость подготовки. Ограничение 10¹² и отказ при несовместимом протоколе — осознанная граница первой версии companion, а не маскировка данных.
